# Astra Design System Review

**Soft Spatial Portfolio의 방향은 이 포트폴리오에 타당하다.** 기존에도 헤더·버튼·프로필 프레임에 Glass가 적용되어 있으므로, 새로운 시각 언어를 전면 도입하기보다 기존 표현의 범위를 통제하고 정리하는 성격이 강하다(`current-ui-audit.md` §7·§8). 특히 `visual-direction.md` §0의 **Content = Solid / Control = Glass / Concept = 3D** 구분은 프로젝트 정보의 가독성을 지키는 실용적인 기준이다.

다만 **방향의 타당성과 토큰 조합의 시각적 검증은 별개**다. 인접 Depth의 동일한 값, 테마별 합성 토큰의 적용 조건, Migration을 단순 치환으로 설명한 부분에는 보완이 필요하다. 본 검토는 첨부된 세 문서만 대상으로 한다. 문서에 반영된 헤더 바 Glass 제외 등의 결정은 유효한 것으로 평가하되, 첨부되지 않은 `review-decision.md`의 추가 내용이나 실제 코드 적용 여부는 확인한 것으로 취급하지 않는다.

## 항목별 검토

### 1. 5-Level Depth의 시각적 구분

**Level 1과 Level 2가 구분되지 않을 위험은 문서 값에서 직접 확인된다.**

- `foundation.md` §14에서 다크 테마의 `--bg-elevated`와 `--card`는 모두 `#111827`이다.
- §11은 Level 1에도 `--border`와 `--shadow-xs`를 허용하고, Level 2의 기본값에도 같은 조합을 지정한다. 따라서 허용된 선택만으로 **배경·보더·그림자·블러가 모두 동일한 두 Level**이 만들어질 수 있다.
- 라이트에서는 §13의 `--bg-elevated: #f8fafc`와 `--card: #ffffff`가 다르지만, 같은 보더와 작은 그림자를 사용하면 차이가 충분한지는 확정할 수 없다.

`visual-direction.md` §2-3이 Level을 **그림자 강도가 아닌 역할**로 정의한 것은 타당하다. 그러나 같은 절의 “인접 Level은 최소 하나의 시각 신호가 바뀌어야 한다”는 조건까지 현재 매핑이 보장하지는 않는다.

Level 2→3은 반투명 배경·블러·inset 하이라이트라는 차이가 있지만, 단색 표면 위에서는 블러가 눈에 띄지 않을 수 있다. Level 4는 §11에 따라 에셋에 내장된 조명과 그림자에 의존하므로 Foundation 값만으로 평가할 수 없다.

**판정: 역할 체계는 타당하나, 특히 Level 1/2의 식별성은 브라우저에서 직접 확인 필요.**

### 2. Controlled Glass의 적용 범위

**허용 목록 자체는 문제 없음.** 현재 첨부본에서는 ProjectCard 헤더 바가 더 이상 열린 질문이 아니다.

`visual-direction.md` §0·§2-2와 `foundation.md` §11-2는 제목·설명·타입 배지·피처·스킬 칩을 불투명으로 유지하고, Glass 후보를 Project action·floating control·carousel control로 제한한다. 헤더 바까지 부분 유리화할 수 있다고 해석하는 것은 현재 결정과 맞지 않는다.

다만 다음 표현은 범위를 다시 흐릴 수 있다.

- `foundation.md` §5-2의 **“Level 2→3 전이”**, §8-3의 **“Level이 바뀌는 hover”**는 역할 기반 정의와 맞지 않는다. 카드의 그림자가 강조되어도 콘텐츠가 컨트롤로 바뀌는 것은 아니다. 이 표현을 근거로 카드 배경까지 Glass로 전환하면 §0의 불투명 유지 결정과 충돌한다.
- `visual-direction.md` §2-2의 “액션 영역만”은 같은 절의 **액션 버튼 및 도입 시 floating 트레이**라는 제한과 함께 읽어야 한다. 카드 하단의 스킬 칩까지 포함하는 넓은 영역으로 해석할 근거는 없다.

**판정: 경계 재설계는 불필요하며, 남아 있는 ‘Level 전이’ 표현의 정합성 보완이 필요하다.**

### 3. Light/Dark Glass 재질의 일관성

**같은 재질로 읽힐 가능성은 있지만, 동일한 레시피가 이를 보장하지는 않는다.**

`foundation.md` §13·§14의 차이는 상당하다.

| 재질 요소 | Light | Dark |
|---|---:|---:|
| `--glass-bg` 백색 알파 | 0.55 | 0.08 |
| `--glass-bg-strong` 백색 알파 | 0.75 | 0.16 |
| `--glass-border` 백색 알파 | 0.65 | 0.16 |
| `--glass-highlight` 백색 알파 | 0.85 | 0.22 |
| `--glass-specular` 백색 알파 | 0.95 | 0.30 |

이는 테마별 조정이지 그 자체로 결함은 아니다. 다만 **추측으로는** 라이트가 우윳빛 반투명 판, 다크가 어두운 표면에 얇은 윤곽만 있는 패널처럼 읽힐 수 있다. §6-1의 공통 재질 요소와 고정 `saturate(180%)`만으로 이 차이가 상쇄된다고 볼 수는 없다.

추가로 두 가지 구현 조건이 남는다.

- §16은 기존 `--header-bg`를 유지하지만, §6의 공통 레시피는 `--glass-bg`를 사용한다. 특히 다크의 `--header-bg`는 어두운 RGB의 알파 0.5이고, `--glass-bg`는 백색 알파 0.08이다. 헤더가 어느 배경을 사용하는지에 따라 공통 레시피와의 인상이 달라질 수 있다.
- §14의 **“참조 토큰이 바뀌면 합성 토큰도 자동으로 다크값을 사용한다”는 설명에는 적용 위치 조건이 필요하다.** `:root`와 `[data-theme='dark']`가 같은 요소에 적용되면 성립한다. 반면 테마가 하위 요소에 적용되면, 상위에서 계산되어 상속된 `--shadow-xs`나 `--border-accent-subtle` 등이 하위의 색상 재정의만으로 다시 계산되지는 않는다. `current-ui-audit.md` §0은 속성 기반 테마라는 사실만 제공하므로 실제 적용 위치는 확인되지 않았다.

**판정: 재질 비교와 합성 토큰의 실제 테마 반영 모두 브라우저에서 직접 확인 필요.**

### 4. Foundation Token 총량

**총량만으로 과설계라고 판단할 근거는 부족하다. 다만 문서의 집계는 잘못되어 있다.**

`foundation.md` §12의 고유 이름을 기준으로 세면 다음과 같다. 테마별 재정의는 중복 집계하지 않고, 선택 사항인 `--glass-base`와 deprecated 별칭은 제외한다.

| 분류 | 개수 |
|---|---:|
| Color | 27 |
| Spacing & Layout | 13 |
| Typography | 22 |
| Radius | 5 |
| Shadow | 10 |
| Blur | 4 |
| Motion | 6 |
| Z-index | 6 |
| **CSS 커스텀 프로퍼티 합계** | **93** |
| SCSS Breakpoint 변수 | 4 |

기존 유지 토큰은 Color 24개와 폰트 2개로 **26개**, 신규 CSS 토큰은 **67개**다. §17의 “신규 53종”은 다음 누락에서 발생한다.

- Spacing/Layout을 2개로 집계했지만 `--space-1`~`--space-11`도 신규이므로 실제 13개다.
- 신규 Typography는 17개가 아니라 크기 8개·weight 5개·leading/tracking 7개로 20개다.

`current-ui-audit.md`의 조사 범위가 SCSS 26개 파일·3,594줄이고, §8·§9에서 버튼과 카드 변형이 이미 다수 확인된 점을 고려하면 93개라는 숫자만으로 절반 축소를 요구하기는 어렵다. 또한 `foundation.md` §1-1·§1-7·§4가 Primitive Color 계층, 미사용 상태색, 불필요한 radius 티어를 제외한 결정은 적절하다.

**판정: 전체 규모는 수용 가능. 신규 수와 ‘기존 유지’ 표시는 수정 필요.**

### 5. Spacing 11단계의 필요성

**11단계 자체는 문제 없음. 절반 이하로 줄여도 무방하다고 단정할 근거는 없다.**

`foundation.md` §2-1의 4~72px 범위는 배지 패딩부터 섹션 간격까지 담당한다. `current-ui-audit.md` §3에도 작은 칩·카드 내부·섹션 간격이라는 서로 다른 크기 영역이 실제로 존재한다. §2-2에서 같은 72px인 `--section-gap`과 `--header-offset`을 역할별로 분리한 것도 불필요한 중복이 아니다.

다만 **“각 단계에 기존 값이 있다”는 사실은 11개 모두가 반드시 필요하다는 증거까지는 아니다.** §2-1에는 값별 반복 빈도와 사용처 분포가 없어 추가 축소의 손익을 판단하기 어렵다.

더 명확한 문제는 스냅 영향의 설명이다.

- §2-1의 **56→48px는 4px가 아니라 8px 차이**다.
- 같은 표의 28→24px, 36→32px도 값이 달라지는 작업이다.
- 따라서 §17의 “위험 없음”, “이름만 붙인 것”은 Spacing 정규화 전체에 적용할 수 없다.

**판정: 단계 수보다 값 변경을 무변화 리팩터링처럼 설명한 부분이 위험하다. 스냅 결과는 브라우저에서 직접 확인 필요.**

### 6. Typography 8단계의 적정성

**스케일 개수는 문제 없음.**

`foundation.md` §3-2의 Display·제목 3단계·본문 2단계·Label·Caption은 `current-ui-audit.md` §2-2에서 확인된 히어로, 프로젝트/경력 제목, 본문, 배지, 다이어그램 라벨에 대응한다. 프로젝트 설명이 짧다는 이유만으로 README와 경력 서술까지 포함한 이 역할 구분을 과하다고 보기는 어렵다.

위험은 개수가 아니라 적용 결과다.

- 프로젝트 제목 상한 26→22px는 제목의 강조 정도를 바꾼다.
- InfoHeader 28→32px는 다른 제목과의 상대적 위계를 바꾼다.
- 다이어그램의 8→11px는 약 37.5% 확대이므로 기존 좁은 셀에서 줄바꿈·겹침이 생길 수 있다.

11px 하한이 곧 접근성 충족을 뜻하지도, 11px라는 이유만으로 접근성 실패를 뜻하지도 않는다. 실제 폰트·굵기·대비·확대 결과가 필요하다. §18이 Typography 적용을 고위험으로 분류한 것은 타당하다.

**판정: 세분화는 적절하며, 실제 콘텐츠로 브라우저에서 직접 확인 필요.**

### 7. 3D Concept Icon과 Glass UI의 세계관

**조형 방향은 일관되지만, 같은 광원이라는 주장은 아직 구현 수준에서 검증되지 않았다.**

`visual-direction.md` §2-4의 rounded geometry·minimal detail·orthographic camera·soft top-left lighting은 아이콘 간 스타일을 통제하는 구체적인 기준이다. 그러나 `foundation.md` §5-3의 `inset 0 1px 0`은 상단 하이라이트이지, 그 자체로 **좌상단 방향광**을 나타내지는 않는다. §6의 스페큘러도 시작색과 상단 배치만 있고 방향·범위가 확정되지 않았다.

따라서 광원 방향을 공유한다는 문장만으로 3D 오브젝트와 Glass 표면이 같은 조명 아래 있다고 보장할 수 없다. 특히 정적 이미지에 구워진 translucent glass 표현은 UI 뒤 배경에 반응하는 실제 `backdrop-filter`와 다르게 보일 수 있다.

또한 §2-4가 project type 배지를 우선 적용 대상으로 둔 근거는 “텍스트만 있어 스캔성이 낮음”이다. **작은 배지에 3D 이미지를 추가하면 실제 스캔성이 좋아진다는 것은 아직 가정**이다. 기존 정보 아이콘도 `current-ui-audit.md` §11 기준 28px여서, 작은 크기에서 재질과 실루엣이 유지되는지 확인해야 한다.

**판정: 스타일 충돌을 확정할 근거는 없으며, 실제 에셋과 UI를 함께 브라우저에서 직접 확인 필요.**

### 8. Static WebP 3D 아이콘 전략

**정적 에셋 전략은 이 규모에 적절하다.** 다만 `visual-direction.md` §4의 확정 범위는 PNG/WebP이며, WebP 단일 포맷·해상도·압축·용량은 아직 확정되지 않았다.

**장점**

- §2-3과 `foundation.md` §11의 실시간 Three.js/WebGL 제외는 아이콘을 위해 렌더 루프와 추가 3D 실행 환경을 관리하지 않아도 된다는 이점이 있다.
- §2-4의 카메라·조명·재질을 제작 시 고정할 수 있어 정적 Concept 표현과 잘 맞는다.
- WebP는 투명 배경을 지원하므로 지정된 centered composition·transparent background와 양립한다.

**검증되지 않은 비용**

- `current-ui-audit.md` §11의 기존 `currentColor` 아이콘과 달리 색·조명·그림자가 테마에 자동 적응하지 않는다. 하나의 이미지가 두 테마에서 충분한지, 테마별 이미지가 필요한지는 미확정이다.
- 표시 크기와 DPR에 비해 작은 원본은 흐려질 수 있고, 큰 원본은 작은 배지에서 불필요한 전송·디코딩 비용을 만들 수 있다.
- WebP라는 포맷명만으로 파일 크기가 작다고 보장할 수 없다. §2-4의 여러 개념 후보를 실제로 도입할 때는 개별 파일뿐 아니라 동시 노출되는 에셋의 총량도 확인해야 한다.
- 테마별 파일을 선택한다면 추가 제작·관리 비용이 생긴다. 두 파일을 모두 내려받는지는 실제 로딩 구현에 달려 있다.

**판정: 전략은 문제 없음. 테마 적응·선명도·총 전송량은 브라우저에서 직접 확인 필요.**

### 9. `backdrop-filter` 렌더링 성능

**위험 지점은 다이어그램이나 기술 배지가 아니라, 허용된 액션 컨트롤의 반복 적용이다.**

`visual-direction.md` §2-2가 다이어그램 데이터 카드와 기술 배지에 Glass를 금지한 것은 `current-ui-audit.md` §18-5의 다수 blur 우려를 적절히 차단한다. 이 요소들이 모두 유리화될 것이라고 가정할 이유는 없다.

반면 `current-ui-audit.md` §8의 ProjectCard 액션은 README/video/notion/github/velog 등 여러 개다. 여기에 `foundation.md` §11-2의 Glass 버튼 또는 floating 트레이를 적용하면, **보이는 카드 수 × 액션 수**만큼 필터 대상이 늘어날 가능성이 있다. 트레이와 내부 버튼이 함께 블러를 갖는 중첩 여부도 아직 확정되지 않았다.

성능 판단에는 다음 기존 조건도 포함해야 한다.

- `current-ui-audit.md` §7의 페이지 배경은 `jquery.ripples` WebGL 캔버스를 사용한다.
- §12의 캐러셀은 mask·clip·transform 관련 레이아웃을 이미 포함한다.
- `foundation.md` §7의 8/16/24px만으로 비용을 예측할 수는 없다. 필터 면적, 중첩, 배경 변화, 동시 노출 수가 함께 작용한다.

**판정: 단일 버튼 정지 화면으로는 검증 불가. 실제 캐러셀과 움직이는 배경을 포함해 브라우저에서 직접 확인 필요.**

### 10. Hover/Motion의 장식적 과장 위험

**Reduced Motion 원칙은 문제 없음. 일반 모드의 기존 효과와 신규 효과가 중첩될 위험은 남아 있다.**

`foundation.md` §8-4는 continuous 제거·장식 transform 제거·opacity/color 중심 상태 변화로 정리되어 있다. 이전의 상충된 대응을 현재 문제로 다시 지적할 필요는 없다.

하지만 다음 결정은 아직 연결되지 않았다.

- `visual-direction.md` §2-5는 translate·scale·shadow·specular의 조합을 허용한다. 여기에 `foundation.md` §8-2의 bounce easing까지 적용하면, 각각 작은 값이어도 한 컨트롤의 반응이 과해질 수 있다.
- `current-ui-audit.md` §8의 ProjectCard 버튼에는 이미 `perspective/rotateX` 틸트가 있다. duration/easing 토큰 치환만으로는 이 효과가 새로운 허용 범위에 맞는지 정리되지 않는다.
- `visual-direction.md` §4의 열린 질문 3은 일반 모드의 pulse·shimmer·shine 존치를 여전히 미정으로 둔다.
- `foundation.md` §18은 Glass 적용을 14번, continuous 정리를 15번으로 배치한다. 중간 결과에서 기존 `1.8s infinite` CTA 효과와 신규 Glass hover가 함께 남으면 “장식적 지속 애니메이션을 사용하지 않는다”는 §2-5 원칙과 어긋날 수 있다.

캐러셀 idle float의 JS 구현 여부는 감사에서도 **추정**이다. 또한 배경 WebGL은 CSS의 reduced-motion 선언만으로 중단된다고 볼 수 없다(`current-ui-audit.md` §7·§13-2).

**판정: 모션 원칙은 타당하나, 기존 효과의 존치를 미룬 채 신규 효과를 추가하는 단계는 주의가 필요하다.**

### 11. 접근성: 대비·테마 전환·포커스·3D

**WCAG AA 목표는 명확하지만, 현재 토큰 유지가 목표 충족을 뜻하지는 않는다.**

- **텍스트 대비:** `visual-direction.md` §2-1은 작은 텍스트 4.5:1을 요구한다. 그런데 `foundation.md` §13의 `--text-muted: #6b7280`와 `--bg-muted: #f1f6ff` 조합은 불투명 색상 계산 기준 약 **4.46:1**이다. 실제 작은 라벨에 이 조합이 사용되는지는 확인이 필요하지만, 모든 기존 색상 조합이 안전하다고 간주할 수는 없다.
- **Glass 위 텍스트:** §6의 반투명 배경과 hover 시 배경 변경은 뒤 콘텐츠에 따라 최종 대비를 바꾼다. 토큰의 RGBA 값만 비교해서 판정할 수 없다.
- **테마 전환:** §14의 합성 토큰 적용 조건이 맞지 않으면 다크 텍스트·표면과 라이트용 보더·그림자가 혼재할 수 있다. 실제 전환 중 색상 애니메이션이 있다면 중간 상태도 검증 대상이다.
- **포커스:** `visual-direction.md` §2-2의 hover 액션 트레이에는 키보드 노출·포커스 가시성 조건이 아직 없다. hover에서 보인다는 것만으로 키보드와 터치에서도 액션을 사용할 수 있다고 볼 수 없다.
- **비텍스트 정보:** 조작을 식별하는 데 필요한 아이콘·상태 표시는 주변과의 대비도 확인해야 한다. 다만 모든 장식적 Glass 테두리에 일괄적으로 3:1을 요구할 이유는 없다.
- **3D 의미:** §0의 Concept 원칙에 따르면 3D가 사라져도 프로젝트 식별 정보는 유지되어야 한다. project type 이미지 추가 시 기존 텍스트와 중복 낭독되는지, 이미지가 없을 때 의미가 손실되는지는 에셋 명세만으로 확인되지 않는다.

**판정: 실제 실패 범위는 브라우저에서 직접 확인 필요. 특히 hover 트레이와 Glass 텍스트는 PoC의 필수 통과 조건이다.**

### 12. ProjectCard PoC에 남은 가정

**본문 불투명·헤더 바 제외는 확정 사항이다. 미검증 사항은 다음과 같다.**

1. **어떤 Glass 표현을 실제로 사용하는가.**  
   `foundation.md` §7은 GlassButton·캐러셀 버튼의 최종 blur 배정을 유보하고, §11-2는 트레이 구현을 유보한다. 이 선택에 따라 재질·대비·필터 수가 달라진다.

2. **지역 스택이 실제로 격리되는가.**  
   §10-2의 `position: relative` 컨테이너 설명만으로 stacking context가 생기지는 않는다. 또한 §11의 “컨테이너 z-index를 상속”은 CSS 기본 동작을 정확히 설명하지 않는다. 카드 내부 액션은 Local stacking일 수 있는데, 같은 표의 Level 3 예시는 Global 토큰 범위로만 적혀 있어 그대로 적용하면 혼동할 수 있다. 이는 역할 Level과 실제 겹침 순서를 별도로 확인해야 하는 이유다.

3. **캐러셀 안에서도 효과와 포커스가 잘리지 않는가.**  
   `current-ui-audit.md` §12의 mask·overflow clip 구조는 카드 외곽 그림자, hover 이동, floating 트레이, 포커스 표시와 충돌할 가능성이 있다. 단독 카드 렌더링으로는 판정할 수 없다.

4. **기존 전역 SCSS와 함께 안전한가.**  
   `current-ui-audit.md` §9·§15-4는 `ProjectCard.scss`와 `ReadMe.scss`가 같은 피처·링크 셀렉터를 재정의한다고 기록한다. 중복이 남아 있다면 PoC 단독 성공이 README를 연 상태의 결과까지 보장하지 않는다.

5. **실제 정보 밀도에서도 Content First가 유지되는가.**  
   `foundation.md` §3-2의 제목 크기 변경과 `visual-direction.md` §2-4의 타입 아이콘 추가가 긴 제목·많은 배지·여러 액션이 있는 카드에서도 스캔성을 높이는지는 미검증이다.

**판정: PoC가 필요한 이유는 새로운 경계를 설계하기 위해서가 아니라, 이미 정한 경계가 실제 조합에서도 성립하는지 확인하기 위해서다.**

## Simplify

전체 토큰 수를 일괄 축소할 근거는 부족하다. 과설계로 번질 수 있는 부분은 다음 두 가지로 제한된다.

- **선택적 `--glass-base`의 추가는 현재 불필요하다.**  
  `foundation.md` §1-6도 이를 디자인 의미가 아닌 RGB 반복 제거로 설명하고 확정 목록에서 제외했다. 같은 백색 채널을 쓰는 다크는 공유하지 않고 라이트에만 추상화를 추가하는 편의가, 이 규모에서 별도 관리 지점을 정당화한다고 보기 어렵다. **현재의 미도입 판단을 유지하는 것이 타당하다.**

- **`--blur-md: 16px`의 필요성을 검증 전에 확정한 설명은 근거보다 앞서 있다.**  
  `foundation.md` §7은 기존 일치 값이 없음을 인정하면서도 “8px는 부유 신호로 약하다”는 이유로 사용이 확정되었다고 서술한다. 그러나 같은 절에서 컴포넌트별 배정은 PoC로 유보한다. 중간 티어가 실제로 필요한지는 아직 시각적으로 입증되지 않았다. **문제는 16px라는 값 자체보다, 미검증 단계를 필수 세분화로 확정한 데 있다.**

Spacing 11단계, Typography 8단계, Global z-index 6개는 현재 사용처와 연결되어 있어 추가 축소를 요구하지 않는다(`foundation.md` §2·§3·§10). `/design-system` 역시 범용 문서 도구를 목표로 하지 않는다고 명시하므로, 계획만으로 엔터프라이즈급 과설계라고 판단하지 않는다(`visual-direction.md` §5).

  근거: `foundation.md` §6.

- **Motion/Reduced Motion:** 기존 pulse·shimmer·tilt와 신규 hover의 중첩, JS 기반 모션 및 배경 효과의 감소 설정 반영을 확인한다. 캐러셀 idle float의 존재 자체도 확인 대상이다.
