# Astra Design System Review

“Soft Spatial Portfolio”의 방향 자체는 1인 개발자 포트폴리오에 적합하다. 기존 색상 토큰을 유지하고, 본문·기술 배지·데이터 카드를 유리화 대상에서 제외하며, 3D를 개념 표현으로 제한한 결정은 현재 UI의 문제와 연결되어 있다(`foundation.md` 원칙 1, `visual-direction.md` §2-1~§2-4). Spacing과 Typography 역시 단계 수만으로 과설계라고 판단할 근거는 부족하다.

다만 Foundation을 그대로 적용하면 방향 문서가 약속한 위계와 접근성이 자동으로 확보되지는 않는다. **Level 1/2의 동일한 조합 허용, Glass 블러 규칙의 상충, 미확정 ProjectCard 경계를 확정 사용처로 취급한 판단, reduced-motion 전략의 모순**은 구현 전에 정리해야 한다. 이 검토는 첨부 문서만을 대상으로 하며, 실제 코드 반영 여부나 렌더링 결과를 확인한 감사는 아니다.

## 항목별 검토

### 1. 5-Level Depth의 시각적 구분

**문서상 구분이 보장되지 않는 조합이 있다.**

- **Level 1과 Level 2는 다크 테마에서 완전히 같아질 수 있다.** `foundation.md` §11은 Level 1에 `--bg-elevated`·`--border`·`--shadow-xs`를 허용하고, Level 2에도 `--card`·`--border`·`--shadow-xs`를 지정한다. §14에서 `--bg-elevated`와 `--card`는 모두 `#111827`이다. 따라서 배경·보더·그림자·블러가 전부 같은 조합이 성립한다. 이는 “차이가 작다”보다 명확한 문제이며, `visual-direction.md` §2-3의 레벨 간 구분 원칙을 충족하지 않는다.
- **라이트의 Level 0/1 및 Level 1/2 구분은 브라우저에서 직접 확인 필요.** `foundation.md` §13의 `--bg`·`--card`는 `#ffffff`, `--bg-elevated`는 `#f8fafc`다. Level 1의 보더·그림자가 선택 사항이므로, 실제 면적과 ambient wash에 따라 표면 차이가 약하게 읽힐 가능성이 있다.
- **Level 2→3은 속성 차이는 있지만 재질 차이가 항상 보이는 것은 아니다.** §11의 블러와 반투명 배경은 명확한 변경이다. 그러나 불투명한 흰색 카드 위에 흰색 반투명 표면을 놓으면 배경색 차이가 사라지고, 균일한 배경에는 블러로 흐릴 디테일도 없다. 이 경우 유리 인상은 외곽 그림자와 경계에 의존한다. **브라우저에서 직접 확인 필요.**
- **Level 2의 기본 그림자 기준도 일관되지 않다.** `visual-direction.md` §2-3은 `sm`~`md`, `foundation.md` §11은 `xs`를 지정한다. 방향 문서의 수치는 예시이므로 변경 자체는 문제없지만, Foundation 내부에서도 §11-1의 README 모달 예시는 `--shadow-lg`를 유지한다. §11을 “그대로 적용”하라는 설명과 개별 예시 중 무엇이 우선인지 불명확하다.

Level 4는 토큰만으로 평가할 수 없다. `foundation.md` §11이 실루엣·그림자를 에셋에 위임했으므로, **5개 레벨 전체의 시각적 구분은 실제 3D 에셋까지 포함해 검증해야 한다.**

### 2. Controlled Glass의 적용 범위

**ProjectCard의 미확정 예외가 일반 허용 규칙으로 굳어질 위험이 있다.**

- `visual-direction.md` §2-2는 ProjectCard 헤더 바와 hover 액션 트레이를 **검토 대상**으로 두며, §4 질문 1에서도 경계를 미확정으로 남긴다. 반면 `foundation.md` §7과 §17은 이를 `--blur-md`가 “쓰일 게 확정된” 근거로 사용한다. **검토 중인 영역을 확정 사용처로 승격한 문서상 비약**이다.
- `visual-direction.md` §2-2가 제목·타입 배지 영역을 “콘텐츠라기보다 UI 크롬”으로 분류한 근거는 약하다. 제목과 프로젝트 유형은 프로젝트 식별 정보이므로, §2-1의 “사라져도 정보를 읽는 데 지장이 없는가?”라는 기준으로 자동 제외할 수 없다. 짧은 텍스트라는 이유만으로 본문과 다른 접근성 조건이 되는 것도 아니다.
- `foundation.md` §5-2의 “Level 2→3 전이”는 hover 그림자 강조를 설명하지만, §11의 Level별 조합을 기계적으로 적용하면 카드 전체의 Glass 승격으로 오독될 수 있다. `visual-direction.md` §2-5가 허용한 것은 **Level 3에 준하는 그림자**이지, 콘텐츠 카드 전체의 반투명화가 아니다.

기술 스택 배지와 프로젝트 타입 배지는 구분해야 한다. 전자는 명시적 금지 대상이고, 후자는 부분 유리화 검토 영역에 포함되어 있다(`visual-direction.md` §2-2). 모든 “배지”에 동일한 Glass 규칙을 적용할 근거는 없다.

### 3. Light/Dark Glass 재질의 일관성

**테마별 값 차이 자체는 문제없지만, 같은 재질로 보인다는 결론은 아직 검증되지 않았다.**

`foundation.md` §13·§14의 주요 차이는 다음과 같다.

| 속성 | Light | Dark |
|---|---:|---:|
| `--glass-bg` 알파 | 0.55 | 0.08 |
| `--glass-bg-strong` 알파 | 0.75 | 0.16 |
| `--glass-border` 알파 | 0.65 | 0.16 |
| `--glass-highlight` 알파 | 0.85 | 0.22 |
| `--glass-specular` 알파 | 0.95 | 0.30 |

밝은 배경과 어두운 배경에서 서로 다른 알파를 쓰는 것은 타당하다. 다만 **추정상** 라이트는 흰색이 채워진 불투명에 가까운 표면, 다크는 배경이 강하게 드러나는 얇은 막처럼 읽힐 가능성이 있다. 동일한 `saturate(180%)`만으로 이 인상 차이가 해소된다고 볼 수 없다. **브라우저에서 직접 확인 필요.**

추가로 두 가지 명세 문제가 있다.

- **블러 규칙이 상충한다.** §6은 모든 Level 3에 `--blur-lg`와 `saturate(180%)`를 고정하고 “변주하지 않는다”고 한다. §7은 ProjectCard에 `--blur-md`가 필요하다고 하고, §11은 `--blur-sm`~`--blur-lg`를 용도별로 허용한다. 현재 문서에는 동일 재질을 판단할 단일 기준이 없다.
- **다크 파생 토큰의 자동 반영에는 조건이 있다.** §14는 `--shadow-xs`나 `--border-accent-subtle`을 재정의하지 않아도 참조 토큰의 다크 값이 자동 반영된다고 설명한다. 이는 `:root`와 테마 재정의가 같은 요소에서 계산되는 경우에는 성립한다. 그러나 테마 속성이 하위 요소에 붙으면, 상위에서 이미 계산되어 상속된 합성 토큰이 하위의 새 참조값으로 다시 계산되지는 않는다. `current-ui-audit.md` §0은 테마 속성의 실제 부착 요소를 명시하지 않는다. **실제 테마 속성 위치와 computed style은 브라우저에서 직접 확인 필요.**

또한 기존 Header의 다크 `--header-bg: rgba(11,18,32,.5)`와 공통 Glass의 백색 `.08`은 다른 조합이다(§14). 기존 토큰 값을 유지했다는 사실과 Header의 재질이 유지된다는 사실은 별개다.

### 4. Foundation Token 총량

**총량만으로는 과설계라고 보기 어렵다. 다만 문서의 집계는 잘못되어 있다.**

`foundation.md` §12의 고유 이름을 기준으로 계산하면 다음과 같다. 테마별 재정의는 중복 집계하지 않았다.

| 카테고리 | CSS 커스텀 프로퍼티 수 |
|---|---:|
| Color | 27 |
| Spacing & Layout | 13 |
| Typography | 22 |
| Radius | 5 |
| Shadow | 10 |
| Blur | 4 |
| Motion | 6 |
| Z-index | 6 |
| **합계** | **93** |

여기에 SCSS Breakpoint 변수 4개를 포함하면 **변수 총 97개**다. `respond-to()`는 토큰으로 세지 않았으며, 선택 사항인 `--glass-base`와 deprecated 별칭도 제외했다.

- 유지 토큰은 Color 24개와 폰트 2개, 총 26개다(§16).
- 따라서 **신규 CSS 토큰은 67개**다.
- §17의 “신규 53종”은 Spacing 11개를 누락했고, 신규 Typography를 실제 20개 대신 17개로 집계했다. §12의 Spacing 신규 표시 누락도 함께 정정해야 한다.

26개 SCSS 파일의 반복값을 정리한다는 범위(`current-ui-audit.md` §0)를 고려하면, 93개라는 숫자만으로 절반을 없애야 한다고 판단할 수 없다. Primitive Color 계층과 사용처 없는 `--warning`·`--info`를 추가하지 않은 결정은 적절하다(`foundation.md` §1-1·§1-7).

다만 §10의 **모든 새 z-index를 전역 표에 먼저 등록하도록 하는 규칙**은 범위가 과하다. §11 자체가 Level 0에 음수 z-index를 허용하지만, 등록된 6개 값은 모두 전역 전경 레이어용 양수다. 지역적인 장식 겹침까지 같은 등록 대상으로 읽히면 포트폴리오에 불필요한 토큰 증가를 유발한다.

### 5. Spacing 11단계의 필요성

**11단계라는 이유만으로 문제 삼을 근거는 없다. 절반 이하로 줄여도 무방하다는 근거 역시 없다.**

`foundation.md` §2-1은 작은 배지 간격부터 72px 섹션 여백까지 기존 사용값을 다룬다. `current-ui-audit.md` §3도 배지 padding 4~10px, 카드 padding 18~24px, 섹션 간격 72px이라는 서로 다른 크기 영역을 확인했다. 이를 최대 5단계로 압축해도 손실이 없다고 단정할 수 없다.

다만 현재 정당화에는 다음 한계가 있다.

- “각 단계가 최소 1곳에 대응한다”는 설명은 **11단계 모두가 반복적으로 필요한지**까지 증명하지 않는다. 특히 40·48·64px의 사용 빈도와 역할별 분포는 문서에 없다.
- §2-1이 나열한 기존 값은 19종이 아니라 **20종**이다.
- **56→48px은 4px이 아니라 8px 감소**다. 라이트박스 padding을 약 14% 줄이는 변경을 계산 오류에 근거해 “영향이 미미하다”고 평가했다.
- §17의 “위험 없음, 이름만 붙인 것”이라는 설명은 6→8px, 14→12px, 28→24px 등 실제 값이 바뀌는 매핑에는 해당하지 않는다.

따라서 문제는 단계 수보다 **스냅 변경의 영향을 과소평가한 것**이다. 밀도가 높은 배지와 라이트박스의 간격 변화는 **브라우저에서 직접 확인 필요**다.

### 6. Typography 8단계의 적합성

**문제 없음 — 단계 수는 실제 콘텐츠 역할과 대체로 맞는다.**

`foundation.md` §3-2는 히어로, 섹션·모달 제목, 카드·경력 제목, 소제목, 본문, 보조 본문, 라벨, 캡션으로 구분한다. 이 역할들은 `current-ui-audit.md` §2-2의 실제 사용처와 연결된다. 14/15px이나 11/12px이 가깝다는 사실만으로 중복 단계라고 판단할 수 없다.

다만 **스케일의 적정성과 치환의 안전성은 별개**다.

- 프로젝트 제목 상한 26→22px, InfoHeader 28→32px, 다이어그램 8→11px은 역할 위계와 줄바꿈을 바꾸는 변경이다(§3-2).
- 특히 캡션 하한 상향은 읽기에는 유리할 수 있지만, 좁은 다이어그램의 수치·라벨이 그대로 들어간다는 보장은 없다.
- §3-2가 기존 `clamp()` 처리를 컴포넌트 단계로 넘겼으므로, 고정 rem 토큰만 적용한 상태를 반응형 타이포그래피 완료로 볼 수 없다.

이 부분을 높은 migration 리스크로 분류한 §18의 판단은 적절하다. **실제 콘텐츠와 확대 상태는 브라우저에서 직접 확인 필요**다.

### 7. 3D Concept Icon과 Glass UI의 조형 일관성

**조형 원칙은 서로 양립 가능하지만, 동일한 조명 세계관은 아직 입증되지 않았다.**

`visual-direction.md` §2-4의 rounded geometry, minimal detail, soft plastic/translucent glass, orthographic camera는 통일된 에셋 묶음을 만들기 위한 충분히 제한적인 기준이다. Plastic과 Glass를 혼합한다는 이유만으로 충돌한다고 판단할 필요는 없다.

다만 광원 연결의 근거는 부족하다.

- §2-4는 Glass의 스페큘러도 “왼쪽 위에서 오는 빛”이라고 전제한다.
- 실제 `foundation.md` §5-3의 하이라이트는 `inset 0 1px 0`으로, 상단 강조는 있지만 좌측 방향성은 없다.
- §6은 `::before`의 “상단 하이라이트 그라디언트 시작색”만 명시하고, 방향과 분포는 확정하지 않는다.

따라서 **상단 림이 있는 CSS 표면과 좌상단 조명이 구워진 3D 아이콘이 같은 광원으로 읽힌다는 것은 가정**이다. 실제 에셋의 하이라이트 위치, 내장 그림자, 다크 배경에서의 윤곽을 함께 비교해야 한다. **브라우저에서 직접 확인 필요.**

또한 §2-4의 “project type 아이콘을 추가하면 스캔성이 개선된다”는 설명은 효과를 미리 확정했다. 작은 배지 안에서 company/team/personal을 더 빨리 구분할 수 있는지는 에셋 없이 판단할 수 없다.

### 8. Static WebP 3D 아이콘 전략

**정적 이미지 전략 자체는 적합하다. 단, 세 문서에는 WebP 채택이 아직 확정되어 있지 않다.**

`visual-direction.md` §4 질문 2는 PNG/WebP 정적 이미지와 실시간 3D 중 선택을 열린 질문으로 남기고, `foundation.md` §11도 에셋 정의를 별도 문서에 위임한다. 아래 평가는 **정적 WebP를 채택할 경우의 조건부 평가**다.

**장점**

- 실시간 3D용 렌더 루프와 런타임 의존성이 필요하지 않아, 정적 개념 표현이라는 목적과 잘 맞는다(`visual-direction.md` §2-4·§4 질문 2).
- 조명·카메라·구도를 에셋에 고정할 수 있어 §2-4의 통일 규칙을 유지하기 쉽다.
- 이미지 자체는 움직이지 않으므로 지속 모션 부담이 없다. 단, 이미지에 붙이는 등장·hover 효과까지 자동으로 reduced-motion 대응이 되는 것은 아니다(`foundation.md` §8-4).

**제약**

- **테마 전환:** 구워진 조명과 그림자는 CSS 테마를 따라 바뀌지 않는다. 반투명 픽셀의 합성은 가능하지만, 실시간 배경을 굴절·반사하는 재질은 아니다. 한 파일이 두 테마에 충분한지, 밝은 테두리나 내장 그림자가 어색한지는 **브라우저에서 직접 확인 필요**다.
- **반응형:** 기존 정보 아이콘은 28px이고, 프로젝트 타입 배지는 현재 아이콘이 없다(`visual-direction.md` §2-4). 실제 표시 크기와 DPR이 정해지지 않아 작은 크기의 식별성과 큰 크기의 선명도를 평가할 수 없다.
- **파일 크기:** WebP라는 포맷만으로 경량을 보장할 수 없다. 제공 문서에는 픽셀 크기·압축 품질·실제 용량이 없으며, 테마별 또는 해상도별 파일이 필요해질 경우의 전송량도 미정이다. **에셋 파일과 Network 측정이 필요**하다.

### 9. `backdrop-filter` 렌더링 성능

**허용 범위를 지키면 위험은 제한적이지만, 단일 컴포넌트의 효과를 반복 배치 성능으로 일반화할 수 없다.**

`current-ui-audit.md` §7의 현재 사용처는 6곳이다. `visual-direction.md` §2-2가 기술 배지와 다이어그램 미니 카드에 Glass를 금지한 것은, 반복 요소의 블러 비용을 제한하는 구체적인 장치다. 이 금지 목록 자체는 문제없다.

위험 지점은 다음과 같다.

- ProjectCard 헤더/트레이까지 확대되면 캐러셀의 여러 카드에 동시에 블러가 적용될 수 있다(`foundation.md` §11-2, `current-ui-audit.md` §12).
- 필터 칩, 카드 CTA, 캐러셀 화살표, Header가 함께 보이는 경우에는 **허용 영역만 사용해도** 여러 필터 표면이 겹친다(`visual-direction.md` §2-2).
- §6의 일괄 24px 규칙은 기존 8px 프로필 유리판과 10px 캐러셀 버튼의 처리 반경을 키운다(`foundation.md` §7). 이 변경이 성능상 무해하다는 근거는 없다.
- `current-ui-audit.md` §7의 `jquery.ripples` WebGL 배경이 계속 갱신된다면 Glass 뒤의 장면도 정적이지 않을 수 있다. 실제 갱신 여부와 영향은 문서만으로 확정할 수 없다.

성능 저하가 발생한다고 단정할 수는 없다. **실제 모바일 기기에서 스크롤·캐러셀 이동 중 Paint/Composite 작업과 프레임 지연을 확인해야 한다.**

### 10. Hover/Motion의 장식적 과장 가능성

**허용 효과의 개별 수치보다 중첩과 기존 효과의 잔존이 위험하다.**

- `visual-direction.md` §2-5는 translate, scale, shadow, specular의 조합을 허용하고 scale 상한 근거로 작은 GlassButton·캐러셀 버튼의 1.05~1.06을 든다. 이를 큰 카드에도 그대로 적용하면 같은 배율이라도 이동하는 시각적 면적이 커진다.
- 카드와 내부 버튼에 각각 1.06이 적용되는 경우, 버튼의 최종 배율은 약 **1.124배**가 된다. 이는 현재 구현 사실이 아니라 **중첩 적용 시 가능한 결과**다. `foundation.md` §8-3이 카드 hover에도 허용한 `--ease-bounce`는 추가적인 오버슈트 가능성이 있다. **브라우저에서 직접 확인 필요.**
- `current-ui-audit.md` §8의 `project-card-btn`에는 기존 `perspective/rotateX` 틸트가 있다. `visual-direction.md` §2-5의 허용 조합과 별도로 남으면, 새 depth 효과가 기존 효과를 대체하지 않고 누적될 수 있다.
- README의 1.8s pulse/shimmer와 Hero의 6s shine은 여전히 존치 미정이다(`visual-direction.md` §2-5·§4 질문 3). `foundation.md` §18은 정리를 마지막 단계로 미루므로, 앞선 토큰 치환만으로 “지속 장식 애니메이션 없음”을 달성했다고 볼 수 없다.
- `current-ui-audit.md` §7의 WebGL 물결 배경은 `visual-direction.md` §2-5의 재검토 목록에 없다. 지속 움직임과 reduced-motion 대응 여부는 **브라우저에서 직접 확인 필요**다. 캐러셀 idle float의 JS 구현은 감사 문서도 추정으로 표시했으므로, 존재가 확정된 애니메이션처럼 취급해서는 안 된다.

### 11. 접근성: 대비·Reduced Motion·포커스

**원칙은 적절하지만, Foundation만으로 준수 여부를 보장할 수 없다.**

**텍스트 대비**

`visual-direction.md` §2-1은 작은 텍스트 4.5:1을 요구한다. 그런데 `foundation.md` §1-3은 `--text-muted`를 라벨에, §1-2는 `--bg-muted`를 배지·보조 표면에 배정하면서 조합 제약을 설명하지 않는다. §13의 두 색 `#6b7280`과 `#f1f6ff`를 불투명 단색으로 조합하면 대비는 **약 4.46:1**이다.

이는 실제 컴포넌트의 사용 조합을 확인한 실패 판정은 아니다. 다만 **기존 토큰 유지가 허용 가능한 모든 조합의 AA 충족을 의미하지는 않음**을 보여준다. Glass에서는 배경 이미지와 hover의 `--glass-bg-strong`까지 포함한 합성 결과를 별도로 확인해야 한다(§6).

**Reduced Motion**

`foundation.md` §8-4 전략 1은 “0에 가깝게 줄이고 즉시 스냅”이라고 설명하면서, 실제 표준 예시는 `keyword-pop 0.35s`로 제시한다. 350ms는 §8-1의 fast 150ms·base 250ms보다 길다. 이 예시만으로 더 짧거나 움직임이 줄었다고 판단할 수 없다.

또한 “완전히 0으로 죽이면 상태 변화를 못 알아차릴 수 있다”는 설명은 최종 상태의 가시성과 전환 중 움직임을 혼동한다. **현재 문구는 일반·축소 모드에서 무엇이 달라져야 하는지 일관되게 정의하지 못한다.**

**포커스와 입력 방식**

`foundation.md` §11은 hover 상태를 설명하지만 포커스 상태는 정의하지 않는다. 특히 `visual-direction.md` §2-2의 “hover 시 나타나는 액션 트레이”는 키보드·터치에서도 액션을 발견하고 실행할 수 있다는 보장이 없다. 이는 새 포커스 토큰의 부재가 아니라 **상태 동작의 미확정 문제**다.

`current-ui-audit.md` §12의 Swiper mask와 overflow clip은 이동한 버튼이나 포커스 표시를 가릴 가능성이 있다. **실제 캐러셀 안에서 브라우저 확인 필요**다.

**3D 아이콘**

`visual-direction.md` §2-4는 개념 매핑만 정의하고 장식 이미지와 정보 이미지의 접근성 역할은 구분하지 않는다. 텍스트 배지와 같은 의미를 반복하는 이미지의 중복 낭독, 이미지가 표시되지 않을 때의 정보 손실을 확인해야 한다. 반면 장식용 3D 에셋의 모든 음영에 일률적인 대비 기준을 적용할 이유는 없다.

### 12. ProjectCard PoC에 남아 있는 가정

**지금 문서만으로는 다음 가정이 검증되지 않았다.**

1. **부분 유리화의 정확한 경계:** 헤더·액션 트레이 중 무엇을 적용할지, 제목·타입 배지를 어떻게 취급할지 미정이다(`visual-direction.md` §4 질문 1).
2. **블러의 유효성:** 카드 내부의 실제 backdrop에 디테일이 있어 8/16/24px 차이가 보일지, 불투명 본문과의 경계가 자연스러울지 미정이다(`foundation.md` §6·§7·§11).
3. **3D 배지의 정보 이득:** 작은 에셋이 프로젝트 유형의 구분을 실제로 돕는다는 근거가 없다(`visual-direction.md` §2-4).
4. **상태 간 가독성:** Light/Dark × 기본/hover/focus × reduced-motion 조합의 결과가 없다(`foundation.md` §8·§11·§13·§14).
5. **캐러셀 내 배치:** 단독 카드에서 정상인 그림자·변형·포커스가 Swiper의 mask/clip 안에서도 보인다는 보장이 없다(`current-ui-audit.md` §12).
6. **스타일 변경의 국소성:** `ProjectCard.scss`와 `ReadMe.scss`는 `project-card-features`·`project-card-link`를 중복 정의한다. ProjectCard 하나의 수정이 README에 영향을 주지 않는다는 가정은 안전하지 않다(`current-ui-audit.md` §9·§15-4).
7. **시각적 Depth와 실제 적층의 일치:** `foundation.md` §11은 Level 3에 전역 z-index 범위를 연결하지만, 카드 안의 Glass라는 이유만으로 Header·모달과 같은 적층 역할이 생기지는 않는다. 실제 겹침과 컨트롤 클릭 가능 여부는 확인되지 않았다.

## Simplify

- **`--blur-md`의 확정 취급은 과도하다.** `foundation.md` §7·§17은 미확정 ProjectCard 부분 유리화를 근거로 16px을 확정한다. `visual-direction.md` §4 질문 1과 `foundation.md` §6의 24px 고정 규칙이 해소되지 않은 상태에서는 필요한 중간 단계라고 입증되지 않았다. 검증 전 확정 목록에 넣은 근거가 부족하다.
- **모든 지역 z-index까지 전역 등록 대상으로 읽히는 규칙은 과하다.** `foundation.md` §10의 6개 전역 레이어 명명은 실제 사용처가 있어 타당하다. 그러나 모든 새 값을 금지하는 범위는 §11의 배경 음수 값 관례와도 충돌하며, 작은 장식의 지역적 겹침까지 Foundation을 늘리는 이유가 된다. 이 규칙의 포괄 범위는 현재 포트폴리오에 비해 넓다.

## Must Validate in Browser

- **인접 Depth 비교:** Light/Dark에서 Level 0~3을 나란히 비교하고, 특히 동일 색·그림자를 허용하는 Level 1/2가 구분되는지 확인한다. Hover 전후도 별도로 비교한다(`foundation.md` §11·§13·§14).
- **실제 Glass backdrop:** ProjectCard 내부의 균일한 표면, ambient wash, 스크린샷 뒤에서 유리감과 텍스트 가독성을 확인한다. 블러 규칙 상충을 먼저 해소해야 한다(§6·§7·§11).
- **테마 합성 토큰:** `data-theme` 부착 요소와 `--shadow-*`·`--border-accent-*`의 실제 computed value를 확인한다. §14의 자동 반영 전제가 맞는지 검증한다.
- **텍스트 대비:** Glass 기본/hover, Header, 라벨·보조 텍스트의 실제 합성 배경에서 4.5:1 충족 여부를 측정한다(`visual-direction.md` §2-1, `foundation.md` §13·§14).
- **3D 재질과 래스터 품질:** 실제 배지·정보 아이콘 크기와 DPR에서 조명 방향, 윤곽, 투명 가장자리, 내장 그림자를 두 테마 모두 확인한다(`visual-direction.md` §2-4). 에셋 공급 전에는 검증 불가다.
- **반복 Glass 성능:** 실제 모바일 기기에서 여러 ProjectCard, Header, 필터·내비게이션이 함께 보일 때 스크롤과 캐러셀 이동을 측정한다. WebGL 배경의 동작 여부도 포함한다(`current-ui-audit.md` §7·§12).
- **모션의 중첩과 축소:** 카드·버튼 hover가 겹칠 때의 최종 변형, 기존 틸트·pulse·shimmer의 잔존, reduced-motion에서 남는 움직임을 확인한다(`visual-direction.md` §2-5, `foundation.md` §8-4).
- **키보드·터치 조작:** Hover 트레이 접근, 포커스 표시의 clip/mask 가림, 모달·캐러셀과의 적층 및 클릭 가능 여부를 확인한다(`visual-direction.md` §2-2, `current-ui-audit.md` §12).
- **정규화에 따른 레이아웃 변화:** Spacing 스냅, 26→22px 제목, 8→11px 캡션, 1280/560px breakpoint 흡수 구간을 실제 콘텐츠와 텍스트 확대 상태로 확인한다(`foundation.md` §2-1·§3-2·§9-2).
- **PoC의 주변 영향:** README의 공유 셀렉터와 캐러셀 안팎 렌더링을 함께 확인한다. 단독 카드 스크린샷만으로 migration 안전성을 판정하지 않는다(`current-ui-audit.md` §9·§12).

## ProjectCard PoC Checklist

### 시각·콘텐츠

- [ ] PoC가 검증하는 Glass 경계를 명시했다. 미선택 후보까지 허용된 것으로 간주하지 않는다(`visual-direction.md` §4 질문 1).
- [ ] Feature 리스트와 스킬 칩 영역은 불투명하게 유지되며, 기술 스택 배지에 블러가 적용되지 않는다(`visual-direction.md` §2-1·§2-2).
- [ ] Light/Dark에서 카드 본문과 인접 Level 1 표면이 구분된다. 기본 상태의 동일 토큰 조합 가능성도 확인했다(`foundation.md` §11·§14).

- [ ] 기본/hover에서 그림자·하이라이트가 과장되거나 본문보다 먼저 시선을 끌지 않는다(`visual-direction.md` §2-1·§2-5).
- [ ] 적용한 경우, 3D 타입 아이콘이 실제 배지 크기에서 식별되고 기존 유형 텍스트의 스캔을 방해하지 않는다(`visual-direction.md` §2-4).

- [ ] 합의된 블러 규칙과 실제 computed style이 일치하고, 카드 전체나 금지 영역에 필터가 불필요하게 확장되지 않았다(`foundation.md` §6·§7·§11).

- [ ] Light/Dark × 기본/hover/focus에서 제목·라벨·보조 텍스트의 대비를 실제 배경 기준으로 확인했다(`visual-direction.md` §2-1).
- [ ] `data-theme` 전환 시 파생 border/shadow 토큰도 실제 다크 값으로 계산되는지 확인했다(`foundation.md` §14).
- [ ] Hover 트레이를 키보드와 터치에서도 발견하고 실행할 수 있으며, 포커스가 항상 보인다(`visual-direction.md` §2-2).
- [ ] Reduced Motion에서 반복 효과가 정지하고, hover·등장 효과가 실제로 축소된다. 350ms 대체 애니메이션이라는 이유만으로 통과시키지 않는다(`foundation.md` §8-4).
- [ ] 기존 `rotateX`, README pulse/shimmer와 신규 효과가 의도 없이 중첩되지 않는다(`current-ui-audit.md` §8, `visual-direction.md` §2-5).
- [ ] 3D 이미지의 장식/정보 역할에 맞게 대체 텍스트를 확인했고, 배지 텍스트와 중복 낭독하거나 이미지 누락 시 유형 정보가 사라지지 않는다(`visual-direction.md` §2-4).

## Final Assessment

**GO WITH CHANGES**

방향 자체를 다시 설계할 이유는 없다. 불투명 콘텐츠 유지와 Glass 금지 목록은 명확한 가치가 있고(`visual-direction.md` §2-1·§2-2), 기존 토큰 재사용과 불필요한 색상 계층 배제도 프로젝트 규모에 맞는다(`foundation.md` §1-1·§1-7). Spacing 11단계와 Typography 8단계를 숫자만 보고 축소할 필요도 없다.

다만 다음 사항은 전체 적용 전에 해소해야 한다.

1. **Depth 기준:** `foundation.md` §11·§14가 허용하는 Level 1/2의 동일 조합과, Level 2 그림자 표·개별 예시의 관계를 정리해야 한다.
2. **Glass 범위와 블러:** §6의 24px 고정과 §7·§11의 용도별 블러를 일치시키고, 미확정 ProjectCard 사용처를 확정 근거로 취급하지 않아야 한다.
3. **접근성:** §8-4의 즉시 스냅/350ms 대체 애니메이션 모순을 해소하고, hover 트레이의 비마우스 조작과 실제 텍스트 대비를 검증해야 한다.
4. **명세 신뢰도:** §17의 신규 토큰 수, §2-1의 spacing 계산 오류, §18의 “1~12번은 저위험 기계적 작업”이라는 포괄적 평가를 바로잡아야 한다. 해당 구간에는 실제 값과 레이아웃이 바뀌는 작업이 포함된다.
5. **검증 범위:** §14의 테마 파생값 전제와 실제 3D 에셋을 확인해야 한다. 정적 WebP는 아직 문서상 확정된 구현 결정이 아니다(`visual-direction.md` §4 질문 2).

**ProjectCard PoC 착수에는 동의한다. 다만 PoC는 현재의 미검증 가정을 확인하는 단계이지, Glass 적용 범위 확대나 Foundation 전체의 시각적 완성도를 승인하는 근거는 아니다.**
